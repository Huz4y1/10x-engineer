# PostgreSQL data types

**Every column has a type, and the type decides what you can store, how much space it takes, and what you can do with it.** Picking the right one up front saves painful migrations later.

Hub: [[PostgreSQL]] · SQL that's special to Postgres: [[PostgreSQL SQL]] · Quick lookup: [[PostgreSQL reference]]

> ✅ **Every SQL example here was run on PostgreSQL 18.** The outputs shown are real.

---

## The short list — what to use 95% of the time

| You're storing… | Use | Not |
|---|---|---|
| An ID that counts up | `bigint GENERATED ALWAYS AS IDENTITY` | `serial` (old style) |
| An ID that's safe to show publicly / generate anywhere | `uuid` | `text` |
| A whole number | `integer`, or `bigint` if it could pass 2 billion | `numeric` |
| **Money** | **`numeric(12, 2)`** | `money`, `real`, `double precision` |
| A measurement (temperature, weight) | `double precision` | `real` (only ~6 digits) |
| Any text | **`text`** | `varchar(255)` "just in case" |
| Yes/no | `boolean` | `integer` 0/1 |
| A date | `date` | `text` |
| **A moment in time** | **`timestamptz`** | `timestamp` (no time zone) |
| A length of time | `interval` | an integer of seconds |
| Flexible nested data | `jsonb` | `json`, or `text` holding JSON |
| A list of simple values | `text[]`, `integer[]` | a comma-separated string |
| A fixed set of choices | `text` + `CHECK`, or an `enum` | free text |

The rest of this note explains each one and the traps.

## Whole numbers

| Type | Size | Range | Use for |
|---|---|---|---|
| `smallint` | 2 bytes | −32,768 to 32,767 | Almost never — the saving is tiny |
| **`integer`** (`int`) | 4 bytes | ±2.1 billion | Counts, quantities, most numbers |
| **`bigint`** | 8 bytes | ±9.2 quintillion | IDs, anything that keeps growing, milliseconds since 1970 |

```sql
CREATE TABLE numbers_demo (
    qty       integer,
    views     bigint,
    tiny      smallint
);
INSERT INTO numbers_demo VALUES (5, 9000000000, 30000);
SELECT * FROM numbers_demo;
```

```
 qty |   views    | tiny
-----+------------+-------
   5 | 9000000000 | 30000
```

> ⚠️ **An `integer` ID column runs out at about 2.1 billion.** That sounds huge until a busy table hits it and every insert fails. **Use `bigint` for IDs** — 4 extra bytes per row is nothing.

> **Postgres refuses numbers that don't fit, instead of wrapping around.** `INSERT INTO numbers_demo (tiny) VALUES (40000)` fails with *smallint out of range*. That's good — some databases silently store the wrong number.

### Auto-numbered IDs — `IDENTITY`

```sql
CREATE TABLE customers (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- Postgres fills this in: 1, 2, 3...
    name  text NOT NULL
);
INSERT INTO customers (name) VALUES ('Ada'), ('Linus') RETURNING id, name;
```

```
 id | name
----+-------
  1 | Ada
  2 | Linus
```

| Style | Say it like this | Notes |
|---|---|---|
| **`GENERATED ALWAYS AS IDENTITY`** | "Postgres always picks the number" | ✅ **The modern standard.** You can't accidentally insert your own ID |
| `GENERATED BY DEFAULT AS IDENTITY` | "Postgres picks unless I give one" | Useful when importing old data with existing IDs |
| `serial` / `bigserial` | The old way | Still works everywhere; creates a separate sequence. Fine to read, don't write new ones |

> **Numbers get skipped, and that's normal.** A failed insert or a rolled-back transaction still uses up its number. IDs are unique, **not** gap-free — never use them as "row count" or invoice numbers that must be consecutive.

## Decimal numbers — and why money is special

| Type | Precision | Exact? | Use for |
|---|---|---|---|
| `real` | ~6 digits | ❌ | Rarely |
| **`double precision`** | ~15 digits | ❌ | Measurements, scientific values, ML features |
| **`numeric(p, s)`** | Up to 131,072 digits | ✅ **Exact** | **Money**, anything that must add up exactly |

`numeric(12, 2)` means *12 digits in total, 2 after the decimal point* — up to `9,999,999,999.99`.

```sql
SELECT 0.1::double precision + 0.2::double precision AS float_sum,
       0.1::numeric + 0.2::numeric                   AS numeric_sum;
```

```
      float_sum      | numeric_sum
---------------------+-------------
 0.30000000000000004 |         0.3
```

> ⚠️ **That's why money must be `numeric`.** Floating point can't store `0.1` exactly, so sums drift by pennies — and an accountant will find them ([[Numerical methods in practice]]).

```sql
CREATE TABLE prices_demo (price numeric(12, 2));
INSERT INTO prices_demo VALUES (19.999);
SELECT price FROM prices_demo;          -- rounded to 2 places on the way in
```

```
 price
-------
 20.00
```

> ⚠️ **Avoid the `money` type.** It depends on a server locale setting, so the same data can display differently on another server, and dividing it gives surprising results. Use `numeric(12, 2)` and store the currency in its own column.

## Text

| Type | Meaning | Use |
|---|---|---|
| **`text`** | Any length | ✅ **The default for all text** |
| `varchar(n)` | Up to *n* characters | Only when the limit is a real rule (e.g. a 2-letter country code) |
| `char(n)` | Exactly *n* — **pads with spaces** | Almost never |

> **In Postgres `text` and `varchar` perform identically.** `varchar(255)` is a habit from other databases where it mattered — here it just adds a limit you'll have to migrate when a name turns out to be 256 characters.

If there *is* a real rule, a `CHECK` constraint says it more clearly than a length:

```sql
CREATE TABLE text_demo (
    country  text CHECK (length(country) = 2),       -- a real rule: always 2 letters
    email    text NOT NULL,
    padded   char(5)
);
INSERT INTO text_demo VALUES ('GB', 'ada@example.com', 'ab');
SELECT country, email, padded, length(padded) AS padded_len, octet_length(padded) AS stored_bytes
FROM text_demo;
```

```
 country |      email      | padded | padded_len | stored_bytes
---------+-----------------+--------+------------+--------------
 GB      | ada@example.com | ab     |          2 |            5
```

> **`char(5)` stored `'ab'` as `'ab   '`** — five bytes, padded with spaces. That's the trap: comparisons and length functions hide the padding, but it's there. Use `text`.

**Case-insensitive text** (e.g. emails): either compare with `lower()` or install the `citext` extension:

```sql
CREATE EXTENSION IF NOT EXISTS citext;
CREATE TABLE users_ci (email citext UNIQUE);
INSERT INTO users_ci VALUES ('Ada@Example.com');
SELECT count(*) FROM users_ci WHERE email = 'ada@example.com';   -- 1: matches regardless of case
```

## True / false

```sql
CREATE TABLE flags_demo (active boolean NOT NULL DEFAULT true);
INSERT INTO flags_demo VALUES (true), (false), (DEFAULT);
SELECT active, count(*) FROM flags_demo GROUP BY active ORDER BY active;
```

```
 active | count
--------+-------
 f      |     1
 t      |     2
```

> **psql shows `t` and `f`.** In Python (psycopg, SQLAlchemy) you get real `True` / `False`.

> ⚠️ **A boolean without `NOT NULL` has three states:** true, false and null. `WHERE NOT active` skips the null rows. Add `NOT NULL DEFAULT false` unless "unknown" genuinely means something.

## Dates and times — read this one carefully

| Type | Holds | Example | Use for |
|---|---|---|---|
| `date` | A calendar day | `2026-03-17` | Birthdays, invoice dates |
| **`timestamptz`** | **An exact moment**, stored in UTC | `2026-03-17 14:30:00+00` | ✅ **Anything that "happened"** — orders, logins, readings |
| `timestamp` | A date and clock time **with no time zone** | `2026-03-17 14:30:00` | Rarely — a wall-clock time that isn't a moment |
| `time` | Clock time only | `09:00:00` | Opening hours |
| `interval` | A length of time | `2 hours 30 minutes` | Durations, "7 days from now" |

### The `timestamptz` rule

**`timestamptz` doesn't store a time zone — it stores a moment.** It converts whatever you give it to UTC, and converts back to *your session's* time zone when showing it.

```sql
CREATE TABLE events_demo (happened_at timestamptz NOT NULL DEFAULT now());
INSERT INTO events_demo VALUES ('2026-03-17 14:30:00+01');     -- 14:30 in a UTC+1 zone

SET TIME ZONE 'UTC';
SELECT happened_at FROM events_demo;
```

```
      happened_at
------------------------
 2026-03-17 13:30:00+00
```

```sql
SET TIME ZONE 'Europe/London';
SELECT happened_at,
       happened_at AT TIME ZONE 'America/New_York' AS new_york_clock
FROM events_demo;
```

```
      happened_at       |   new_york_clock
------------------------+---------------------
 2026-03-17 13:30:00+00 | 2026-03-17 09:30:00
```

It's the **same moment** shown two ways. The stored value never changed.

> ⚠️ **Why not plain `timestamp`?** It throws away the time zone. `2026-03-29 01:30` in London doesn't even exist (the clocks jump forward), and a server moving to another region silently shifts every value. With `timestamptz` the moment is fixed and only the display changes.

> **Store in `timestamptz`, show in local time.** Convert with `AT TIME ZONE` (or in your app) only when displaying to a person.

### Date and time arithmetic

```sql
SELECT date '2026-01-31' + 1                        AS next_day,       -- date + integer = days
       date '2026-01-31' + interval '1 month'       AS plus_month,     -- clamps to end of February
       timestamptz '2026-03-17 12:00+00' - interval '90 minutes' AS earlier,
       date '2026-12-25' - date '2026-03-17'        AS days_between,   -- date - date = integer days
       age(date '2026-03-17', date '2000-06-01')    AS age;
```

```
  next_day  |     plus_month      |        earlier         | days_between |           age
------------+---------------------+------------------------+--------------+-------------------------
 2026-02-01 | 2026-02-28 00:00:00 | 2026-03-17 10:30:00+00 |          283 | 25 years 9 mons 16 days
```

| Function | Gives |
|---|---|
| `now()` | Current moment (start of the transaction) |
| `current_date` | Today |
| `date_trunc('month', ts)` | Round down — `2026-03-17 14:30` → `2026-03-01 00:00` |
| `extract(year FROM ts)` / `extract(dow FROM ts)` | A part — `dow` is 0 = Sunday |
| `to_char(ts, 'DD Mon YYYY')` | Format for display |
| `to_date('17/03/2026', 'DD/MM/YYYY')` | Parse text that isn't ISO |

> ⚠️ **`now()` is frozen for the whole transaction.** Ten inserts inside one transaction all get the same `now()`. Use `clock_timestamp()` if you need the real time at each statement.

## UUIDs

A **UUID** is a 128-bit random-looking ID like `019a3c2e-7b4f-7a10-b3c1-5d2e9f0a1b2c`. Unlike `1, 2, 3`, anyone can generate one without asking the database, and they don't reveal how many rows you have.

```sql
CREATE TABLE orders_uuid (
    id          uuid PRIMARY KEY DEFAULT uuidv7(),    -- PostgreSQL 18+
    created_at  timestamptz NOT NULL DEFAULT now()
);
INSERT INTO orders_uuid DEFAULT VALUES;
INSERT INTO orders_uuid DEFAULT VALUES;
SELECT id FROM orders_uuid ORDER BY id;
```

| Function | Version | Ordered by time? | Available |
|---|---|---|---|
| **`uuidv7()`** | v7 | ✅ Yes — new IDs sort after old ones | **PostgreSQL 18+** |
| `gen_random_uuid()` | v4 | ❌ Fully random | PostgreSQL 13+ |

> **Prefer `uuidv7()` on Postgres 18.** Random v4 IDs land all over the index, which makes inserts slower on big tables. v7 IDs start with a timestamp, so they arrive in order — nearly as index-friendly as `1, 2, 3`. On older servers, use `gen_random_uuid()`.

> **`bigint` identity or UUID?** `bigint` is smaller and simpler for internal tables. Use a UUID when the ID appears in URLs (so people can't guess `/orders/41`, `/orders/42`), or when rows are created in several places before reaching the database.

## JSON — `jsonb`

For data whose shape varies: settings, API responses, event payloads.

| Type | Stored as | Use |
|---|---|---|
| **`jsonb`** | Parsed binary | ✅ **Always use this one** — fast to query, can be indexed |
| `json` | The exact original text | Only if you must keep key order and whitespace exactly |

```sql
CREATE TABLE devices (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    info  jsonb NOT NULL
);
INSERT INTO devices (info) VALUES
  ('{"model": "ESP32", "sensors": ["temp", "humidity"], "config": {"interval_s": 30}}'),
  ('{"model": "RP2040", "sensors": ["temp"], "config": {"interval_s": 60}}');

SELECT info -> 'config'                    AS config_json,     -- -> returns jsonb
       info ->> 'model'                    AS model_text,      -- ->> returns text
       (info #>> '{config,interval_s}')::int AS interval_s     -- a nested path, cast to a number
FROM devices;
```

```
     config_json      | model_text | interval_s
----------------------+------------+------------
 {"interval_s": 30}   | ESP32      |         30
 {"interval_s": 60}   | RP2040     |         60
```

The querying operators (`@>`, `?`, updating keys, indexing) are in [[PostgreSQL SQL]].

> ⚠️ **JSON is not a substitute for columns.** If every row has a `model` and you filter by it, make it a real `text` column — it gets a proper type, constraints and ordinary indexes. Use `jsonb` for the parts that genuinely vary.

## Arrays

Any type can be an array: `text[]`, `integer[]`, `uuid[]`.

```sql
CREATE TABLE posts (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tags  text[] NOT NULL DEFAULT '{}'
);
INSERT INTO posts (tags) VALUES (ARRAY['python', 'spark']), ('{sql,postgres}');

SELECT id,
       tags,
       tags[1]                  AS first_tag,     -- arrays start at 1, not 0
       cardinality(tags)        AS how_many,
       'sql' = ANY(tags)        AS mentions_sql
FROM posts;
```

```
 id |      tags      | first_tag | how_many | mentions_sql
----+----------------+-----------+----------+--------------
  1 | {python,spark} | python    |        2 | f
  2 | {sql,postgres} | sql       |        2 | t
```

> ⚠️ **Arrays start at 1 in Postgres**, not 0 like Python.

> **Arrays are for simple lists that belong to one row** (tags, a few phone numbers). If the items have their own details, or you often search across them, use a separate table instead ([[Data modeling]]).

## A fixed set of choices — enum or CHECK

```sql
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');

CREATE TABLE orders_enum (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status  order_status NOT NULL DEFAULT 'pending'
);

CREATE TABLE orders_check (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status  text NOT NULL DEFAULT 'pending'
            CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled'))
);
```

| | `ENUM` | `text` + `CHECK` |
|---|---|---|
| Add a value | `ALTER TYPE order_status ADD VALUE 'refunded';` — easy | Replace the constraint — easy |
| **Remove or rename a value** | **Painful** — no `DROP VALUE` | Replace the constraint — easy |
| Sort order | Order you defined | Alphabetical |

> **Default to `text` + `CHECK`.** Enums are tidy but hard to change, and the list of statuses always changes.

## Other types worth knowing

| Type | Holds | Example |
|---|---|---|
| `bytea` | Raw bytes | A small file, a hash. **Large files belong in object storage** ([[Object storage]]) — store the path |
| `inet` / `cidr` | IP address / network | `'192.168.1.10'`, `'10.0.0.0/8'` — supports "is this IP in that network?" |
| `tstzrange` / `daterange` / `int4range` | A range | A booking from 10:00 to 12:00; stops double-bookings with an exclusion constraint |
| `tsvector` / `tsquery` | Full-text search | See [[PostgreSQL SQL]] |
| `point`, `polygon` … | Simple geometry | For real maps use the **PostGIS** extension |
| `vector` | An embedding (list of floats) | From the **pgvector** extension — AI similarity search ([[How to use ML on data]]) |

## Changing a column's type

```sql
CREATE TABLE change_demo (amount text);
INSERT INTO change_demo VALUES ('19.99'), ('5');

ALTER TABLE change_demo
    ALTER COLUMN amount TYPE numeric(12, 2) USING amount::numeric(12, 2);   -- USING says HOW to convert

SELECT amount FROM change_demo;
```

> ⚠️ **Changing a column's type rewrites the whole table and locks it** while it runs. On a big production table that's downtime. For large tables, add a new column, fill it in batches, then swap — or at least do it in a quiet period.

> ⚠️ **A value that can't convert fails the whole `ALTER`** — nothing changes. That's safe, but check first: `SELECT amount FROM change_demo WHERE amount !~ '^\d+(\.\d+)?$';` lists the rows that would break.

## Casting — changing a value's type in a query

```sql
SELECT '42'::integer              AS postgres_style,     -- :: is Postgres shorthand
       CAST('42' AS integer)      AS standard_sql,       -- the same, standard SQL
       '2026-03-17'::date         AS a_date,
       '1 day'::interval          AS an_interval,
       42::text || ' items'       AS joined_text;
```

> **A bad cast is an error, not a null.** `'abc'::integer` fails the whole query. (Spark does the opposite and quietly returns null — [[PySpark reference]].)

## How Postgres types map to your other tools

| PostgreSQL | Python (psycopg / SQLAlchemy) | pandas | PySpark | Notes |
|---|---|---|---|---|
| `integer` / `bigint` | `int` | `int64` | `IntegerType` / `LongType` | |
| `numeric(p,s)` | `decimal.Decimal` | `object` (Decimals) | `DecimalType(p,s)` | Keep it Decimal for money |
| `double precision` | `float` | `float64` | `DoubleType` | |
| `text` / `varchar` | `str` | `object` / `string` | `StringType` | |
| `boolean` | `bool` | `bool` | `BooleanType` | Nulls make pandas use `object` |
| `date` | `datetime.date` | `datetime64` | `DateType` | |
| `timestamptz` | `datetime` **with tzinfo** | `datetime64[ns, UTC]` | `TimestampType` | Spark shows it in the session time zone |
| `uuid` | `uuid.UUID` | `object` | `StringType` | |
| `jsonb` | `dict` / `list` | `object` | `StringType` (parse with `from_json`) | |
| `text[]` | `list` | `object` | `ArrayType(StringType())` | |

In SQLAlchemy the Postgres-only types (`JSONB`, `ARRAY`, `UUID`) come from `sqlalchemy.dialects.postgresql` — see [[PostgreSQL with SQLAlchemy]].

## Common mistakes

| Mistake | What goes wrong | Use instead |
|---|---|---|
| `integer` IDs | Inserts fail around 2.1 billion | `bigint` |
| `double precision` for money | Totals off by pennies | `numeric(12, 2)` |
| `money` type | Depends on server locale | `numeric` + a currency column |
| `timestamp` for events | Time zone lost; DST gaps | `timestamptz` |
| Dates stored as text | Won't sort or compare correctly | `date` / `timestamptz` |
| `varchar(255)` everywhere | Arbitrary limits to migrate later | `text` (+ `CHECK` for real rules) |
| `char(n)` | Silent space padding | `text` |
| Boolean without `NOT NULL` | Three states; `NOT x` skips nulls | `boolean NOT NULL DEFAULT false` |
| `json` | Slower, can't index well | `jsonb` |
| Enums for changing lists | Can't remove values | `text` + `CHECK` |
| Arrays for data that has details | Hard to query and update | A separate table |
| `gen_random_uuid()` on PG 18 | Slower inserts on big tables | `uuidv7()` |
